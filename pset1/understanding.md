## Incremental Hashing with XXH3

`XXH3_createState()` allocates and returns a state object (`XXH3_state_t*`).

A state object is useful when you want to compute a hash **incrementally** rather than hashing an entire buffer at once.

`XXH3_64bits_reset(_ctx[0])` initializes or resets the hash state so that it is ready to compute a new 64-bit XXH3 hash.

## std::unique_ptr<T>

`std::unique_ptr<T>` is a smart pointer that:

- **Owns** an object of type `T`.
- **Automatically destroys** the object when the pointer goes out of scope.
- Ensures there is only **one owning** `unique_ptr` at a time.

## gRPC Stub

In gRPC, a **stub** is a client-side proxy for a remote service. It lets your C++ code call methods on a server as if they were ordinary local methods, while gRPC handles the network communication.

### `RPCGame::NewStub(channel)`

`RPCGame` is a class generated by the Protocol Buffers compiler (`protoc`) from your `.proto` definition.

For example, your `.proto` might contain:

```proto
service RPCGame {
   rpc Play(GameRequest) returns (GameResponse);
}
```

The generated code provides a factory method:

```cpp
RPCGame::NewStub(channel)
```

This creates a client-side stub connected to the server through the supplied gRPC channel.

## Command-Line Parsing with getopt()

It uses `getopt()`, a POSIX function for parsing command-line options.

```cpp
while ((ch = getopt(argc, argv, "h:n:f:")) != -1)
```

The third argument, `"h:n:f:"`, specifies which options are accepted. The **colon** (`:`) means that the option must be followed by a value.

For example:

```bash
./program -h localhost:50051 -n 100 -f input.txt
```

`optarg` is a global variable provided by `getopt()`. It points to the argument associated with the currently parsed option.

For example, when parsing `./program -h localhost:50051`:

- `ch` becomes `'h'`.
- `optarg` points to `"localhost:50051"`.

## One-Shot Hashing

`XXH3_64bits(name, name_len)` computes an XXH3 64-bit hash of the data pointed to by `name`, using `name_len` bytes.

Unlike `XXH3_64bits_update()`, this is a **one-shot** hash function. It computes the hash directly without requiring a hash state.

## Windowing / Async RPC

In **synchronous** gRPC, you make an RPC and wait for its response. In **asynchronous** gRPC, you initiate operations, and gRPC notifies you when those operations complete.

There are four central concepts:

1. Completion Queue (CQ)
2. Completion events
3. Tags
4. RPC lifecycle

Notice that responses can arrive in a **different order** from the order in which requests were sent. This creates a problem:

> How does the client know which request completed?

That's where **Completion Queues** and **tags** come in. Think of a CQ as an **event mailbox**. Whenever an asynchronous operation completes, gRPC puts a completion event into this mailbox.

### Tag

Suppose you initiate three RPCs:

- RPC 1
- RPC 2
- RPC 3

When an RPC completes, an event gets inserted into the CQ. But how do you identify which RPC generated that event?

You attach a **tag** to each asynchronous operation. Think of a tag as an application-defined identifier attached to an operation.

### Example

Suppose you want to send 3 RPCs concurrently.

1. **Initiate RPCs** — Create three RPCs and associate them with a Completion Queue.
2. **Register completion operations** — For each RPC, tell gRPC that you want to be notified when its final result is available. Attach a different tag to each operation.
3. **RPCs execute concurrently** — gRPC handles the networking and communication with the server. Your application can perform other work.
4. **Events arrive** — Suppose RPC 3 finishes first. gRPC inserts an event into the CQ with tag 3.
5. **Application consumes events** — Your event-consumer thread retrieves the event, sees tag 3, and processes RPC 3's result.

### AsyncTry()

`AsyncTry()` returns a pointer to a `ClientAsyncResponseReader<TryResponse>` object. This object represents the in-flight RPC and gives you an interface to interact with it.

### Finish()

The actual templated gRPC interface is:

```cpp
void Finish(
    Response* response,
    grpc::Status* status,
    void* tag
);
```

It registers an asynchronous completion operation.

When the RPC finishes:

1. gRPC populates your response object.
2. gRPC populates your status object.
3. gRPC places a completion event in the associated CompletionQueue, carrying your tag.

## Server-Side Asynchronous Programming Models

gRPC C++ provides two main asynchronous server-side programming models:

1. **Completion Queue (CQ)** API — uses `AsyncService`.
2. **Callback** API — uses `CallbackService` and reactors.

Both are asynchronous, but they expose asynchronous execution differently.

With the Completion Queue API, you manage the event loop and RPC state machines yourself.

With the Callback API, gRPC manages request dispatch and completion; you implement callbacks and optionally manage reactor state.

Suppose a client invokes:
stub->Try(&context, request, &response);

The server receives the request and needs to process it.

In a synchronous server, gRPC invokes your handler, and a server worker thread remains occupied while the handler executes.
grpc::Status Try(
grpc::ServerContext* context,
const TryRequest* request,
TryResponse\* response
) {
uint64_t value = process(request);
response->set_value(std::to_string(value));
return grpc::Status::OK;
}

The handler returns only after processing finishes.

In an asynchronous server, you separate the arrival and completion of RPCs from the application's processing logic.

This allows the server to handle many outstanding RPCs without dedicating a blocked thread to every RPC.

There are two ways to program this asynchronous behavior.

Approach 1: Completion Queue API (AsyncService)
The Completion Queue is gRPC's lowest-level async API — it's the machinery that the callback and future approaches are built on top of. Instead of callbacks or futures, you get an event loop where you poll for events and identify them by a tag (an opaque pointer you choose yourself, usually a state-machine object).

Lets look at it from the lens of TryCall:

If you see serverstub.cc:128, we create a TryCall object by passing asyncService and cq pointer to TryCall constructor. Constructor calls Proceed which move TryCall state machine from 'create' to 'Process'.

Then we loop until cq gets shutdown (cq->Next returns false when cq gets shutdown).

The server implementation requests an RPC call (serverstub.cc:34) with a tag and then waits for the completion queue to return the tag (serverstub.cc:170).
